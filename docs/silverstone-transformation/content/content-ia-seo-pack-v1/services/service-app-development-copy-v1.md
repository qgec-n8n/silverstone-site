## The problem this service addresses

App projects become expensive when the first scope is a collection of ideas rather than a validated user journey. A focused product definition reduces rework and makes technical decisions easier to explain.

## Outcomes to design for

- A defined product that solves one priority problem
- A usable first release with clear ownership
- Integration with the systems that matter
- A roadmap based on evidence rather than assumptions

These are design objectives, not promised results. Agree the baseline, owner and measurement method during discovery.

## What the service can include

- Product discovery and requirements
- User journeys and prototype
- Web or mobile application development
- Authentication and role design where required
- API and system integrations
- Testing, documentation and staged release

The final scope should state what Silverstone owns, what the client owns, which systems are involved and how changes are approved.

## Common use cases

- A customer portal for repeat actions
- A staff tool replacing fragile spreadsheets
- A booking, intake or document workflow
- A mobile companion for an existing service
- A prototype used to test demand before a larger build

## Delivery process

1. **Discovery:** Understand the current journey, users, systems and failure points.
2. **Definition:** Agree the first outcome, constraints, data, handoffs and acceptance criteria.
3. **Design:** Produce the content, flow, prototype or technical plan needed to test the approach.
4. **Build:** Implement the agreed release with clear ownership and change control.
5. **Validate:** Test normal, error, mobile, accessibility and exception paths appropriate to the service.
6. **Handover and review:** Document operation, support, monitoring and the next decision point.

## Fit and boundaries

**A useful fit**
- A repeated problem has an accountable owner.
- The people who perform the work can explain the current process.
- Relevant systems and policies can be reviewed.
- The business is willing to start with a defined scope.
- Success can be observed without inventing a target.

**Not included by default**
- A fixed outcome before discovery
- Unsupported security or compliance claims
- A large build without a validated first release

## Questions buyers often ask

### Do we need iOS and Android on day one?

Only when the user journey and distribution need justify it. A responsive web app or one platform may be the safer first release.

### Can it connect to our current software?

Possibly, but integration depends on the vendor, API, permissions, data quality and commercial terms.

### How do we avoid a project that never finishes?

Define the first user, first task, acceptance criteria and release boundary before adding secondary features.
